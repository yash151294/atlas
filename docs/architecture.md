# Architecture notes and decisions

## Flow
SharePoint (Word/PDF) → **bronze** `documents` (text as received, sha, filename fields) → **detect** (Presidio ∪ Claude structured extraction with a role per person: source, contributor, third_party, private; controlled region and sector → `spans`, `doc_meta`) → **resolve** (3-tier; only sources, contributors and professionally described third parties become entities → `entities`, `mentions`, `review_queue`, `links`) → **redact** (stable tokens, per-document who-is-who legend → `redacted`, `vault`) → **qa** (residual scan, risk score, tier; auto-approval by policy → `qa`) → **graph** (`sources`, `edges` incl. MENTIONED, `people`, `contributors`) → **index** (turn-based chunks, context header + legend, embeddings → `chunks`; `net_index` for network search) → **load** (Delta serving tables in the lakehouse; the Eventhouse's external table; the app's cache) → surfaces (Network, Research, Review; Compliance and Quality for governance).

## Decisions (ADR style)
1. **One extraction pass, two products.** Both use cases need the same facts per document. Extract once, store with provenance; graph and retained copy cannot drift.
2. **Pseudonymise with a vault, not delete.** Stable tokens keep the corpus readable and joinable to the graph; the token → identity map is a separate table with its own retention and access log. Reversible with a reason; erasure = delete vault rows. Policy dial: full / pseudonym_vault / descriptor_only.
3. **Two PII detectors unioned.** Presidio (deterministic floor, cheap, in-tenancy) plus a model (context: who is the source, family and financial details). Lone detector in the 0.5 to 0.85 band → review. Recall over precision.
4. **Identity resolution in three tiers.** Deterministic keys (Salesforce id; name + organisation; filename beats model), scored fuzzy with organisation agreement, human queue. People never auto-merged on fuzzy evidence alone.
5. **Relational edges, not a graph database.** One to three hops; recursive SQL. The edge table is already a property graph, so Graph in Fabric (GQL over the same OneLake tables) is the upgrade when path depth or graph algorithms earn it; a separate graph database would not improve accuracy, which comes from extraction and resolution upstream.
6. **Anthropic contextual retrieval.** Turn-based chunks, Claude-written context per chunk (cached prefix), contextual BM25 + contextual embeddings, RRF, cross-encoder rerank, top-20 to the model, citations mandatory. Local BGE models for the demo; swap by parameter.
7. **Kedro-shaped without Kedro.** Pure nodes, a declarative `PIPELINE` of nodes with named catalog inputs and outputs, a generic runner, parameters, manifest, tests. Kedro is the production framework; not adding the dependency for a four-day build. Dagster is the alternative to name (asset lineage) but it is a service, and the stack already has Fabric for orchestration.
8. **Fabric by script.** REST + OneLake DFS from `fabric/deploy.py`; notebooks install the same wheel. Infrastructure as code from day one.
9. **Degraded mode.** If the model is unavailable, detection falls back to Presidio and headers are empty; the pipeline still runs and the Evals page shows the recall gap.
10. **Every model call in a ledger.** Purpose, tokens, cache hits, cost, provider, prompt version; per-document and per-answer cost shown on the Quality page.
11. **Role-aware pseudonymisation (13 Sep).** The extraction pass classifies every person. Sources and professional third parties keep a descriptor next to their token and become graph nodes; private individuals are removed and never become entities. Rules-only name hits the model did not place are treated as private (recall-first, graph stays clean). A same-document nickname with the same title and organisation is the same person.
12. **Approval gate instead of per-document approval (13 Sep).** Residual scan (leaked values, contact patterns, NER on the retained text, an independent second model), risk score, tier. Auto-approve below a threshold by a named policy; human queue above; random audit sample with its issue rate reported. See `docs/compliance.md`.
13. **Contributor-centric network (13 Sep).** Search by contributor name gives the profile; anything else gives contributors ranked by reach = Σ match × recency over matched sources, plus second-degree reach through MENTIONED edges. Match = min-max-normalised embedding similarity of the person's descriptor line plus exact term overlap, thresholded. Region and sector are controlled vocabularies from the extraction pass.
14. **Agentic-lite retrieval, not GraphRAG (13 Sep).** A fast planner decomposes the question into 1 to 4 searches and structured filters drawn from the graph's vocabulary; searches run in parallel and fuse by reciprocal rank; rerank against the original question; the answer is a structured briefing (headline, findings with citations, timeline, gaps, follow-ups); citations are validated deterministically and unsupported findings are dropped. Threads carry history into the planner and the answer. Community-summary GraphRAG was rejected: rebuild cost at every ingest, and it answers corpus-wide theme questions an analyst here rarely asks.
15. **Retention and rights as code (13 Sep).** `atlas/retention.py`: report, enforce (raw deletion, vault expiry), subject lookup, erasure; all logged.
16. **One user, no app-level roles (13 Sep, second pass).** The 'acting as' switch and `acl.yaml` were removed: an application filter is the wrong layer for a confidentiality rule. Production scope is Entra plus OneLake security on the engagement column; the retrieval query is unchanged. Nav is three analyst tasks (Network, Research, Review) plus two governance pages.
17. **Special-category and offence content is detected, counted and priced into the gate (13 Sep, second pass).** The residual model pass returns Art. 9/10 categories stated about a person in the retained copy; listed as a reason, weighted in the risk score by a dial, counted on Quality. Pseudonymisation does not take such content outside Art. 9, so an operator needs a Schedule 1 condition; the product's job is to know where it is.
18. **Names inside clauses are split out before the span merge (13 Sep, second pass).** A FINANCIAL, FAMILY or ADDRESS clause that contains a person's name is cut around the name in `detect.split_around_people`, so the name stays a PERSON mention with an entity and a stable token, and the rest of the clause keeps its own type. Found when the extraction prompt started returning whole clauses: the merge had been typing the clause as PERSON and storing a sentence in the vault as a name.
19. **The gate scores model-confirmed residuals, shows rules-only ones (13 Sep, second pass).** NER alone on a retained copy names streets, towers and companies as people (13 of 14 hits were not people); those are listed as informational and only leaked values, contact patterns and the second model's names score. The special-category flag is a legal-basis signal, weighted 0.1, not a leak. The strict per-type extraction prompt needed by gpt-5-mini is a parameter (`detect.strict_types`), off on Claude where it costs FINANCIAL and FAMILY recall.
20. **One data plane (13 Sep, third pass).** The catalog root is the Fabric lakehouse in production (`ATLAS_ROOT=abfss://…` in `.env`) and a laptop folder in development; working files under `Files/`, serving tables as Delta under `Tables/` written by the load node with delta-rs; `atlas/store.py` is the only door to storage (ADLS DFS API for files, delta-rs for tables, DuckDB for reads). The app holds an in-memory DuckDB cache of the serving tables, refreshed at startup and after each write, so requests take milliseconds and storage is read once per refresh. The pipeline runs as a scheduled Fabric notebook (`10_pipeline`) with the same wheel; retention as `20_retention`.
21. **Retrieval runs in the Eventhouse over the Delta table it never copies (13 Sep, third pass).** `atlas/eventhouse.py` creates an external Delta table over `Tables/gold_chunks` and answers `index.retrieve` with `series_cosine_similarity`, keyword term hits and reciprocal-rank fusion, filters first. No ingestion step, one source of truth. In development (no `EVENTHOUSE_URI`) the cache's BM25 and cosine scan answer the same call. `mode` is honoured on both engines (15 Sep, found in use): the Eventhouse branch had served only `hybrid` and the single-index modes fell back to DuckDB, so the retrieval eval had been comparing DuckDB's BM25 against KQL's term hits in one table and the results read as keyword search beating the full stack. Zeroing a leg's RRF weight leaves the other leg's ranking, and a keyword-only query breaks its term-count ties by `chunk_id` rather than by cosine, so the row measures the keyword leg alone; each eval row now records the engine that served it. On the engine the app runs on, pass@5 is keyword 0.80, embeddings 0.68, fused 0.76, fused + rerank 0.88; on the DuckDB path, whose keyword leg is real BM25, the same four are 0.96, 0.68, 0.80, 0.88. The gap between the two keyword rows is the term-count scorer and is the first tuning item; that keyword alone still wins at five on DuckDB is the golden set, whose questions were written from the chunks they answer.

22. **Azure AI Search built, measured and removed (13 Sep).** One index (HNSW vector field, BM25, semantic ranker), 334 passages; agreement with the app 13 to 18 of 20 because the service fuses and reranks its own way. Deleted the same day: a separate billed service running a different query is not what this stack needs.
23. **Identity is Microsoft Entra (13 Sep, third pass).** The app signs users in with the auth-code flow against the tenant (app registration `atlas-app`, `ENTRA_*` in `.env`, `APP_URL` for the redirect), keeps a signed session cookie, refuses every page and API call without one, and records the signed-in UPN on every approval, span decision, reveal, audit verdict and erasure, plus a sign-in event in `access_log.jsonl`. Without `ENTRA_*` the app runs as one named analyst (development). Engagement scope stays a platform property (OneLake security); the app never filters by user.
24. **The Azure OpenAI client is plain REST (13 Sep, third pass).** `atlas/llm_azure.py` calls the chat and embeddings endpoints over the retrying HTTP session with the key or an Entra token; the `openai` SDK and its `aiohttp` dependency are gone, so the same wheel runs unchanged inside a Fabric notebook whose runtime pins older libraries. Anthropic keeps its SDK (it needs only httpx).
25. **The app runs on Azure Container Apps in UK South (13 Sep, third pass).** `azure/deploy_app.py`: image built locally for linux/amd64 (ACR Tasks are not permitted on the subscription) and pushed to ACR; Container App with a system-assigned managed identity that pulls the image, reads and writes OneLake and queries the Eventhouse; the identity sits in one Entra security group for which the Fabric setting "Service principals can use Fabric APIs" is enabled, and is a Contributor on the workspace; sign-in limited to users assigned to the Entra app; secrets as Container Apps secrets; the image fails closed without sign-in configuration. A five-lens adversarial review (71 agents) before the first build drove: no package cache in the image, the spaCy model surviving the final sync, upload names sanitised, a non-root user owning only its upload folder, timed session cookies, `/healthz` as a readiness signal, identity and Fabric access before the serving revision, research threads owned by the page. One identity path in the container: DuckDB never talks to storage; delta-rs and the DFS API use the azure-identity token.
26. **Writes are atomic, mutations serialised, consistency by re-derivation (13 Sep, review pass).** Every working file (parquet, json, uploads) is written whole to a `.tmp` sibling and renamed into place (`os.replace` locally, the ADLS rename call on OneLake), so a reader never sees a partial file; Delta serving tables were already single atomic commits; logs are append-only. The app holds one process-wide lock around every read-modify-write endpoint (approve, audit verdict, span decision, manual redaction, identity decision, upload, retention run, erasure), so two analysts cannot lose each other's update on the same table; per-document locks are the upgrade if throughput ever needs it. Nothing spans two files transactionally: downstream tables are always recomputed from upstream ones by the pipeline, which is how consistency is restored after any partial run. What is not ACID and is said so: a crash between writing the parquet working copy and the Delta serving copy leaves them one step apart until the next load.
27. **The pipeline notebook takes its resume step as a Fabric parameter, and a code deploy never touches data (13 Sep, review pass).** `deploy.py --from resolve` had been baking `ATLAS_FROM` into the notebook's environment, so the nightly schedule would have skipped ingest and detect for ever; the step is now a tagged parameters cell (`FROM_STEP`) that the job API overrides for one run only. `deploy.py` uploads the wheel, conf and notebooks by default and the laptop's raw files and parquet layers only with `--data`, because production writes those files (approvals, decisions, logs) and a redeploy from a laptop must not overwrite them.
28. **The app's read model is an in-memory DuckDB (13 Sep, review pass, stated).** Every request reads the serving cache, never storage; the cache is rebuilt from the Delta tables at startup and after each write, and holds the FTS index on the passages and the network's descriptor matrix (unit-normalised once per refresh, so a network search is one matrix product). Query embeddings are memoised per process. What is deliberately not cached: briefings, which are always answered live so the page shows the real latency. The working files a document review needs (raw text, mentions, vault, review queue) are not serving tables; on OneLake the store memoises each per process until it is written or a full refresh follows a run elsewhere, so opening a document is not four storage reads (15 Sep).
29. **Extraction is incremental and the app follows the schedule (13 Sep, review pass).** The detect node takes last run's `silver_spans` and `silver_doc_meta` as optional inputs and keeps them for every document whose text hash (`sha256`, stored in the metadata) is unchanged, so a nightly run costs nothing unless files changed; `ATLAS_FORCE_DETECT=1` re-extracts everything after a prompt or model change. The app polls the run manifest every five minutes and refreshes its serving cache when a run has finished elsewhere, so the 02:00 notebook's output reaches the analysts without a restart.
30. **Human decisions are durable across runs (13 Sep, review pass, found in use).** A full pipeline run rebuilds every silver table, and until now only approvals were carried over: a reviewer's manual redactions, restored spans, identity decisions and audit verdicts would have been lost at the next 02:00 run. `pipeline._resolve` re-applies identity and span decisions from the previous mentions and queue tables; `pipeline._redact` carries approvals and audit verdicts and re-applies manual redactions (`redact.reapply_manual`, renumbering a token only if the run has issued it to something else). Test: `test_human_decisions_survive_a_rerun`.
31. **Manual redaction is whole-word, organisation-safe, token-consistent and reversible (14 Sep, found in use).** A reviewer's "redact it" used to replace every substring, so the surname 'Kurosawa' cut into 'Kurosawa Heavy Industries' six times; the gate's second model had flagged that surname although it only occurred inside company names. `redact.manual_redact` now matches whole words, never inside an organisation name known to the entities table, reuses the token of a person the document already holds (by canonical name or alias), and adds a new token to the who-is-who legend as a private individual; `redact.undo_manual` reverses a manual redaction from the Review page. The gate no longer counts a model-flagged name that is part of an organisation name in the text. The Review page highlights residual hits in the text before tokens become markup, which is what had corrupted a token's tooltip into visible HTML.
32. **A lone surname resolves to the one person the document already holds (14 Sep, found in use).** The rules engine had found 'Ogata' after the model had placed 'Masaru Ogata'; a rules-only name was informational by ADR 19, so the surname stayed in the retained copy, the gate flagged it, and the reviewer's manual redaction minted a second token for the same person. `Resolver.same_doc_name` now links a single name token to the one PERSON entity seen in that document (source, contributor or professional) whose name carries it; two candidates stay ambiguous and informational, for the gate. The same rule guides a reviewer's manual redaction. Two defects found in the same run: a human approval lost its mode across runs and was re-decided as policy (the mode now travels with the approval), and worker threads appending to one OneLake log partition raced on the file length and failed (appends are serialised per process and retried once).
33. **The analyst surface keeps only what an analyst does (14 Sep, feedback).** The audit-sample tab and verdict buttons, the upload card and the Quality page left the app. An audit read by the same analyst the policy serves proved little; the gate's random draw (`audit_sample`, `audit_sample_rate`, `audit_seed`) and the carry of audit verdicts across runs went with the tab, since a flag nothing reads is dead state. If audit reads return with a compliance role (ADR 16), the draw is three lines in `qa.gate`. Intake is the raw folder on OneLake and the scheduled notebook only; the live single-file path (`add_document`) went with the upload. The evaluation numbers come from `atlas.evals.snapshot`, which the write-up and the DPIA quote, not from a page analysts never open. Subject lookups on the Compliance page now log who, the request reference and the entity ids found, the shape of a vault reveal: a name lookup is the one bypass of pseudonymisation the right of access requires, and it left no trace. The Research mode selector (research, sourcing, regulatory) went too: it changed one sentence of the writing instruction and the planner already reads the shape of the question.
34. **Open work survives leaving the page (14 Sep, feedback).** Moving between Network, Research and Review used to drop the Research thread, the Network search and the document under review. All three pages now keep what is open in the browser's localStorage (the thread as questions and briefings; the search as query, filters and the open profile or source; the review as list tab, open document and view) and rebuild from it on return; New thread or Clear empties it, and a link carrying `?q=` or `?doc=` wins. The browser, not the server, holds it: ADR 25 keeps the server free of session state, storage is per browser profile, and a revealed value is a DOM decoration that is never written, so a shared workstation shows the next person a pseudonymised thread at worst.
35. **The research desk traverses the network, computed not generated (14 Sep).** The planner classifies a network question (reach, path, neighbourhood) and names its ends; `network.traverse` answers it from the edge table in the serving cache: reach through the same search the Network page runs, shortest chains by a layered breadth-first search that keeps every parent so tied routes surface ("also via"), a neighbourhood as everyone within N hops with the node it was reached through. An end resolves a token exactly, a contributor or an organisation by fuzzy name, a description through the descriptor index. Topic edges are left out of paths (they would join everyone through "compliance"). The headline and the Network block are computed and the answer model never sees the graph, so nothing new needs a citation or a checker; text findings sit below as what the passages say, and a pure network question skips retrieval and the answer model (about a second). The answer model is told the reach part is already answered and must not be the subject of its headline (`answer.NET_TASK`, 15 Sep): the older wording said only "answered separately, write about the passages", and a briefing opened "The corpus does not state who can reach a compliance officer at a Gulf bank" directly beneath a computed block naming the four contributors who can. Observed once; four controlled runs of the old wording did not reproduce it, so the new wording is the more explicit instruction rather than a demonstrated fix, and the flag rate is unchanged by it (30% against 35% of findings over four runs each). Every briefing that cites transcripts ends with who can re-approach the sources cited, from the INTERVIEWED edges. Rejected: an agent with graph tools (ADR 14's reasons) and feeding the graph to the model as evidence (a place to misstate a date the table already holds). Test: `test_research_traverses_the_network`.

36. **The analyst surface has one design system, and a landing page stands before sign-in (15 Sep, feedback).** The pages had a utilitarian look. `base.css` is now one system of tokens (off-white paper, white cards with soft corners, a navy header with a mint active state, peach for attention, Helvetica Neue Light for display and Medium for headings), with one reveal per page, a cross-fade between pages through the view-transition API, skeleton placeholders instead of spinners, and everything switched off under reduced motion. A visitor without a session lands on `/welcome` (the mark, one line, Sign in with Microsoft) and returns to the page they asked for after sign-in, the destination validated as a path on this app. The signed-in user and the review-queue count are inlined into every page as `window.ATLAS`, and the shared script runs inside the body, so the header is complete at first paint and two round trips per page are gone. Every feature and every script behaviour is unchanged; only the visual layer, the shell and the sign-in path moved.
37. **Home is an analytics page over the serving tables (15 Sep, feedback).** The home page carried three task cards, the run manifest per node and six log rows: the header already names the tasks, the node table is engineering, the logs are on Compliance. It now shows the shape of the network from the tables the app already serves: a coverage matrix of regions by sectors whose number is the source count and whose fill is reach today (the sum of the Network search's own recency decay, so Home and Network agree on what reach means; a blank cell is a gap), with each region's holders and last contact beside it; the pace of interviews over 24 months; contributors by sources reached, grey after a year quiet; and the gate as a dot histogram of risk scores against the policy line. Every figure is computed from the cache in one request (`/api/home`, `network.overview`) and every sentence on the page is computed, never written. Rejected on the data: a topic map (326 topics across 37 sources), second-degree people by region (they carry none), research usage (threads are page-held), retention clocks (Compliance, ADR 33). The page ends with when the tables were last refreshed and nothing else about the run.
38. **The application is called Atlas (15 Sep, feedback).** A sentence describing what the thing does is not a name, and a product needs one, so the application is Atlas: a map of who can reach whom, and the memory behind it. The name sits in one place in each surface: a `.lock` lockup in `app/static` used by the header and the landing panel, and the tab title `Atlas · <page>`. Extraction runs once and produces one product that answers two questions.

39. **A pseudonym token is identity, so it is carried across runs (15 Sep, found in use).** `redact_all` numbered tokens by order of first encounter across the corpus, so a new file that sorted early re-numbered everyone: measured on the demo corpus, one document moved to the front changed the token of 199 of 199 people and the `source_token` of 52 of 52 documents. `[PERSON_0012]` in a briefing an analyst exported yesterday meant a different person after the next nightly run, and every chunk's text changed, so every embedding was recomputed for nothing. `redact._seed_counters` now seeds the counter from the previous vault and mints new numbers above the highest already held; `pipeline._redact` also seeds the source tokens of sources never named in the body, which have no vault row and accounted for 8 of the 52. The first seed was keyed the way `redact_all` keys tokens, entity id for people and organisations, and that was only half the fix (16 Sep): entity ids are positional too, allocated in first-encounter order with every contributor from the Salesforce export ahead of the sources, so appending five contributor rows re-pointed 185 of 316 ids and re-issued 185 of 199 person tokens, and a new transcript sorting early re-issued 33. The seed is now keyed by the normalised values the vault holds against each token, matched against the entity's canonical name and aliases, with a number another key already took skipped; per-document tokens (private individuals, contact details) and manual redactions keep their own keys, which never move. Re-running the redact step reproduces the committed corpus exactly, 52 of 52 documents byte for byte and 777 of 777 vault rows, so adopting it costs no re-tokenisation, and the same measurement now re-issues nothing in all three scenarios. The same pass removed a phantom: a deliverable has no source entity, the parquet null is truthy, and every deliverable was handed one shared `source_token` no vault row backed. Tests: `test_tokens_survive_a_new_document`, `test_tokens_survive_renumbered_entity_ids`.
40. **The headline is checked like a finding (15 Sep, found in use).** The independent checker read every finding against its cited passages but never the headline, which is the one sentence an analyst reads aloud and the one most likely to generalise past the evidence. Found on the demo question: a briefing led with "about eleven months" while the checker was rejecting that same figure in the finding below it. `answer.ask` now appends the headline to the same `verify` call as one more unit, cited to the union of what the findings cite, so it costs no extra latency (the same thread pool) and uses the same rubric; a headline the checker cannot support is shown with its reason, exactly as a finding is. The note attaches to whichever sentence the model wrote: on a network question the displayed headline is computed from the edge table and is never checked (ADR 35), so the note sits under the text headline instead. `verify` must return its verdicts in input order for this to be safe; `test_verify_keeps_the_order_it_was_given` pins it.
41. **The research desk is reproducible up to the model, and that boundary is measured, not assumed (15 Sep).** A briefing's findings vary run to run: 8, 7 and 6 findings with 7, 6 and 4 verified for one question. The cause is not retrieval. Same query repeated in one process and across processes, on both engines and in all three modes, returns an identical top 20; holding the plan fixed, `gather` and the reranker return one unique evidence set over four runs. The variance is the three model calls, and no knob removes it: on the deployment the app uses, `temperature=0` and `top_p` are rejected outright ("only the default (1) is supported") and `seed` is accepted but does not pin the sample, while the Claude 5 API has no temperature parameter at all — `output_config.effort` replaced it. The planner is the amplifier, because it changes the evidence itself: one run in three returned boolean keyword strings instead of the prose queries its prompt asks for, and scored worst. What does hold on every run is groundedness: `dropped` was 0 throughout, meaning the answer model never cited a chunk it was not shown. Extraction varies the same way (39, 40 and 40 spans on three passes of one document), which is why redaction recall is quoted as of a run and not as a constant.

42. **A region the query names is a filter, and a match shows the phrase it came from (15 Sep, found in use).** Searching the network for "compliance at a gulf bank" returned a contributor whose only matching source was a former General Counsel at a US pharmaceutical company. Two causes. The score is `0.55 x min-max-normalised cosine + 0.45 x term overlap` against the whole indexed line, which carries the descriptor, former organisations, region, country, sector, seniority and the access topics; that source's topics read "central bank supervision Nigeria" and "external compliance review", so 'compliance' and 'bank' both hit, two of three terms scored 0.667 and the total cleared the 0.5 threshold by 0.02. The page shows only the descriptor, so the match chips named words the visible text did not contain. And 'gulf', the one term that would have excluded a US pharma source and the Nigerian contact behind it, matched nothing and nothing required it to: overlap has no AND, and region is a controlled vocabulary the free-text box never consulted. `network.vocab_filters` now reads a region or sector the query names, applies it as a filter (an explicit one from the page always wins) and spends those words rather than ranking on them; `network.where` returns the phrase of the indexed line each hit came from, which the page shows in place of the bare word. The rule is asymmetric on purpose: a region is a place name, so either half of "Japan & Korea" reaches it, while a sector must be named in full, because "payments", "legal" and "regulator" are words an analyst types without meaning a filter. The same query now ranks the former Head of Compliance at Meridian Gulf Bank first at 1.0, and every matched source is in the Gulf. Test: `test_a_region_in_the_query_filters_and_is_not_ranked_on`.

43. **Determinism stops at the model; the machinery to hide that was built, measured and reverted (16 Sep).** A briefing's findings moved between runs of the same question (8, 7 and 6 findings; 7, 6 and 4 supported by the checker), so the variance was decomposed rather than argued about. Retrieval is not the cause and never was: one query returns one top-20 within a process, across processes, on both engines and in all three modes, and with the plan held fixed `gather` and the reranker return a single evidence set over four runs. Nor can the generation be pinned. On the deployment the app uses, `temperature=0` is refused ("only the default (1) is supported"), `top_p` is refused, and `seed` is accepted but the same seed returns different text; the Claude 5 API has no temperature parameter at all, `output_config.effort` having replaced it. With the evidence frozen byte-identical, five runs still produced 5 to 7 findings and 0 to 4 flags, so the variance is the writing, not the reading. Tightening the answer prompt against invented figures did not reduce it either (31% of findings flagged against 43%, five runs each).
    Built and then reverted: pinning a question's plan and its briefing so repeats returned the same words, and drawing three briefings in parallel to keep the best by checker verdict. It met the goal — five questions, five repeats each, byte-identical within a process and across processes, repeats at 0.4s against 25s — and was reverted as inelegant, which it is. A pin is a cache dressed as a guarantee: it freezes one draw of a lottery and the draw it freezes is arbitrary. Nine draws of one question had the checker supporting between 0 and 6 findings, so a single pinned draw carries a 67% chance of three or more flagged findings; best-of-three lowers that to 24% but costs 2.9x per new briefing ($0.0340 against $0.0119) and still pins a lottery. The remaining honest position is the boundary itself: the evidence is reproducible and measured to be, the prose is not, and a briefing that must not move is an artefact to be saved rather than a query to be re-run (see "research threads persisted beyond the browser page", below).
    Two retrieval findings from the same experiments were reverted with the rest and are worth reapplying on their own merits, being about recall rather than variance. On the 25 golden questions at k=12 the literal question finds the answering chunk 0.96 of the time against 0.84 for the planner's one-to-four generated queries, with no question the decomposition found that the literal question missed and three the other way. The planner's filters cost a further 16 points (0.96 down to 0.80) and it set them on 15 of the 25 questions, because `filter_clause` narrows on `source_region` and `source_sector`, which describe the interviewee rather than the passage: a question about the Gulf excluded a Gulf report whose source sits elsewhere. Both are a parameter and a few lines if the recall is wanted back.

44. **The application names only itself (16 Sep).** A demo link is forwarded, and wherever it lands the reader takes the mark at the top as the owner, so the rule is one line: nothing an analyst or a visitor can see names anything but Atlas.
    The mark: `atlas-mark.svg`, a globe reduced to three parallels with one point marked on the middle line, which is what the product is: a map, and the place on it this network reaches. The point sits on a line that runs past it on both sides, so it reads as a place rather than a pin dropped on a map; three earlier drafts put it at the end of the top parallel and every one of them read as a lollipop at 24px. `favicon.svg` carries the same geometry on a navy tile, because the mark is off-white and a transparent one disappears on a light tab strip; each page links it in its own head, as it does the stylesheet, so the icon is right at first paint. The mark sits 10px from the word (13px on the landing panel), and the word stays text rather than joining the image, so it scales, recolours and is read aloud. The tab title is `Atlas · <page>`; the landing lead reads "built from the interview transcripts you already write. Sign in with your work account"; Home's headline is "Where the network reaches today"; the FastAPI title and the development UPN (`analyst@atlas.local`) follow.
    Surface includes view-source, so the names a browser can be made to show follow the copy: `window.ATLAS`, the page-state keys `atlas.network`, `atlas.research` and `atlas.review`, and the cookies `atlas_s`, `atlas_state` and `atlas_next`.

45. **An exact name is evidence; a disagreeing organisation is a question, not a split (16 Sep).** The deterministic tier linked two people on a normalised name alone: the organisation check guarded only the fuzzy tier. Measured on the corpus, 17 mentions were linked by an exact name, 11 with organisations that agree (correct cross-document identity: one person named in three transcripts of the same engagement) and 6 that disagree, of which four were doubtful — a central banker and someone at the company under investigation as one node, a regulator and a Geneva placement agent, a lone forename 'Rashid' matched to Rashid Kanaan across engagements. Splitting them automatically was rejected: it loses the person who changed employer, and an organisation is often a description ('external consultant to PayNaira' against 'PayNaira Ltd', which scores 62). So the link stands and the queue gets the question, with both organisations in the reason; a reviewer rejecting it turns that mention into its own private token, which is why `pipeline._resolve` and `docs_queue` now apply a rejection to exact links as well as provisional ones. In the same tier, a provisional link no longer contributes an alias: 'Tadashi Kurosawa', linked to Takeshi in the review band, became an alias and every later mention then matched *exactly*, hardening a guess into a merge a rejection could not unpick. Effect on the corpus: no entity split and no mention moved (930 compared), the identity queue goes from 1 question to 5, and three or four documents cross the gate's line into human review because an unresolved identity question is worth 0.15 — the gate doing what it is for (41 of 52 by policy on the deployed corpus after the change, 44 before; the exact count moves by a document between runs because the gate's second reader is a model). Tests: `test_a_same_name_at_another_organisation_is_queued_not_merged_in_silence`, `test_a_provisional_link_never_hardens_into_an_alias`.

46. **A contributor who has left is marked, not hidden (16 Sep).** The Salesforce export carries `Status__c` and nothing read it, so a leaver looked exactly as reachable as anyone else on Network and on Home — the one page that answers "where can we reach today". Deleting them was never the option: their interviews are the provenance of every source they found, and the answer to "a contributor leaves" has always been that the edges stay as history. The status now travels from the export through the entity to `gold_contributors`, and the surfaces that name a contributor show it beside their base. Ranking is deliberately untouched: reach still counts what they reached, the way a quiet contributor is marked rather than demoted, and whether a leaver should drop out of reach entirely is a policy question for whoever operates it, not a default the software should pick. Test: `test_a_contributor_who_has_left_is_marked_not_hidden`.
